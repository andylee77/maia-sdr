# 019 -- Phase 6E.10: Vivado bake artefacts (regen Verilog, regen PAC, wire `m_axi_lsm_dibit` through TCL)

**Date:** 2026-04-10
**Phase:** 6E.10 (Verilog + SVD regen + Vivado wiring for the LSM chain)
**Branch:** fishball-p25
**Status:** HDL side DONE -- regenerated artefacts land cleanly, both TCL files
wired. Vivado synth + on-target validation are the remaining user-driven steps.

---

## Goal

Phase 6E.9 wired `LsmDemod` into `P25Core` at the Amaranth source level, but
the binary HDL artefacts that Vivado actually consumes (`p25_core.v` and the
Rust PAC generated from `p25.svd`) were still the pre-6E.7 versions on disk.
This sub-phase regenerates those artefacts and adds the two TCL one-liners
that surface the new `m_axi_lsm_dibit` AXI master to the Vivado IP packager
and the block-design HP1 SmartConnect.

After 6E.10 the codebase is in a state where running `build_fpga.bat --p25`
produces a bitstream that contains the full LSM HDL chain plus its parallel
dibit DMA ring. The actual Vivado synth + the on-target smoke against the
Clay County NAC 0x8A1 simulcast site are the only Phase 6E items still
pending and live on the user's side because they need Vivado 2023.2 + the
Fishball Z7020 hardware.

## What's new

### Regenerated HDL artefacts

`build_hdl.bat --p25 --verilog-only` (Docker, ~1 min wall clock) regenerated
all three downstream artefacts from the 6E.9 Amaranth source:

| Artefact | Path | Before | After |
|----------|------|--------|-------|
| P25 Verilog | `maia-hdl/ip/p25-core/default/p25_core.v` | 770 KB / 21,896 lines (pre-6E.7) | 1.30 MB / 37,420 lines |
| P25 SVD     | `p25-httpd/p25-pac/p25.svd` | 17,408 bytes / 21 registers (pre-6E.9) | 22,286 bytes / 27 registers |
| P25 Rust PAC | `p25-httpd/p25-pac/src/lib.rs` | (matched old SVD) | 89,999 bytes (auto-regenerated by `svd2rust 0.33.5`) |

The Verilog growth (~70 %) is dominated by the LSM chain: `LsmDemod` and its
11 child Elaboratables, plus the second `DibitPacker` + `DmaStreamRingWrite`
pair for `lsm_dibit_dma`, plus the new `lsm` register bank with its
`RegisterCDC`. A spot grep for `m_axi_lsm_dibit` confirms the new master is
present in the Verilog hierarchy and wired through to `P25Core`'s top-level
ports.

The SVD adds the six `lsm_*` registers from the new bank 5
(`lsm_control`, `lsm_status`, `lsm_nid`, `lsm_drop_count`, `lsm_dibit_next`,
`lsm_debug`) at offsets `0xa0`/`0xa4`/`0xa8`/`0xac`/`0xb0`/`0xb4`. The first
21 registers are byte-for-byte unchanged from the pre-6E.9 SVD, so the
existing `p25-httpd` register accessors against the C4FM chain need no
changes.

The svd2rust regeneration runs automatically inside the same Docker pass
because `build_hdl.sh` carries `svd2rust 0.33.5` in its persistent volume
(installed on first run). The generated PAC compiles cleanly under
`cargo check` -- 33 lifetime-elision warnings, all in the new `lsm_*`
register accessors, which match the same warning pattern svd2rust already
emits for every other register bank in the file (pre-existing convention,
not addressed in this sub-phase).

### `system_bd.tcl` -- HP1 SmartConnect for `m_axi_lsm_dibit`

Added one `ad_mem_hp1_interconnect` call alongside the existing three
(`m_axi_dibit`, `m_axi_traffic`, `m_axi_iq`):

```tcl
ad_mem_hp1_interconnect maia_sdr_clk/clk_out1 p25_core/m_axi_lsm_dibit
```

`ad_mem_hp1_interconnect` is idempotent -- repeated calls extend the same
SmartConnect rather than creating a new one -- so the new master simply
becomes a fourth slave port on the same HP1-bound SmartConnect that already
hosts the C4FM dibit, traffic, and IQ masters. HP1 budget at ~1.7 GB/s
absorbs the additional ~1.28 KB/s from the LSM dibit ring at well below
0.001 % utilisation. The header comment was updated to call out the four
masters explicitly and credit the LSM master to Phase 6E.9.

### `package_ip.tcl` -- bus interface association for `m_axi_lsm_dibit`

Added one `ipx::associate_bus_interfaces` call alongside the existing three:

```tcl
ipx::associate_bus_interfaces -busif m_axi_lsm_dibit -clock clk [ipx::current_core]
```

This is what tells the Vivado IP packager that the new AXI master in the
generated `p25_core.v` lives in the `clk` clock domain (the 100 MHz P25
core clock from `maia_sdr_clk/clk_out1`). Without this line the IP packager
emits the master as an unclocked port and the block design refuses to
auto-connect it to the SmartConnect.

## What 6E.10 does *not* cover (user-side hand-off)

Three things are deliberately left for the user to drive on the Windows
host with Vivado 2023.2 + the Fishball Z7020 hardware:

1. **Run `build_fpga.bat --p25`.** This packages the regenerated
   `p25_core.v` as IP-XACT (using the updated `package_ip.tcl`), sources
   `system_bd.tcl` to build the block design (now with the LSM HP1 wiring),
   then runs Vivado synth/PAR and produces the `.xsa` for Tezuka. Expected
   wall-clock time is ~20 % longer than the pre-6E.9 baseline because the
   Verilog is ~70 % larger. Per the "Build/commit sequencing" rule, the
   resulting `.xsa` should be committed as a separate "shipping artefact"
   commit before it goes into a Tezuka firmware image, and the
   long-running Vivado bake should not be stopped for parallel work.

2. **Tezuka device-tree carve-out for `lsm_dibit_dma`.** The Tezuka
   firmware DT (in `tezuka_fw/board/tezuka/.../devicetree/...`) needs a
   new `p25_lsm_dibit_dma@1a000000` reserved-memory entry alongside the
   existing `p25_dibit_dma@17000000` / `p25_traffic_dma@18000000` /
   `p25_iq_dma@19000000` entries. 32 KB region, 32 KB alignment. Phase 6C
   set the precedent for `iq_dma` -- the LSM dibit ring is mechanically
   identical, just at a new base. This work lives in the Tezuka repo and
   should be coordinated with the same Tezuka build pass that picks up
   the new `.xsa`.

3. **On-target validation against NAC 0x8A1.** With the new bitstream
   loaded and Tezuka booted, set `lsm_control.lsm_enable = 1` and
   `lsm_control.lsm_dibit_dma_enable = 1` via UIO writes against the
   regenerated PAC, point the control DDC at 860.9625 MHz, and confirm:
   - `lsm_status.nid_event` (Rsticky) fires at roughly the expected NID
     cadence (one event per ~14 ms on a busy site).
   - `lsm_status.nid_valid == 1` for those events, with
     `lsm_status.n_errors <= 11`.
   - `lsm_nid.nac == 0x8A1` after the BCH FEC has converged.
   - `lsm_drop_count.drop_count == 0` (the BCH decoder finishes inside
     ~656 µs versus the ~14 ms NID-to-NID gap, so the saturating drop
     counter should never bump).
   - `lsm_status.lsm_dibit_overflow` does not latch (HP1 back-pressure
     never starves the LSM `DibitPacker`).
   - Both `dibit_dma` (C4FM) and `lsm_dibit_dma` (LSM) rings produce
     dibit streams in parallel, and the existing PS-side dibit reader
     can be A/B'd against a future PS-side LSM consumer that drains
     the new ring.

The "AGC deferred to 6E.6.5" caveat from doc 015 is still in force. The
Clay County NAC 0x8A1 site is strong enough that SDRTrunk decodes it
without explicit AGC, so the on-target smoke should still pass against
this specific signal even though `LsmDemod` does not yet have a runtime
AGC. If a weaker simulcast site shows up later in development, AGC needs
to land before the LSM chain can be expected to lock against it.

## Notes for the next session (Phase 6F)

The PS-side `lsm_*` registers are *populated* by the gateware after this
phase but nothing in `p25-httpd` reads them yet. The natural Phase 6F
work is to:

1. Add an `IpCore::read_lsm_status()` / `read_lsm_nid()` accessor pair to
   `p25-httpd/src/fpga.rs` against the new PAC fields.
2. Add a polling loop (60 Hz, dashboard cadence) that drains the
   `lsm_dibit_dma` ring into the existing `LsmPipeline` from Phase 6D
   and surfaces NID events via the existing dashboard WebSocket.
3. Side-by-side both decoders in the dashboard so the operator can
   visually A/B C4FM-from-`dibit_dma` against LSM-from-`lsm_dibit_dma`
   on the same RF capture.
4. Once the HDL LSM chain proves out on hardware, *retire* the Phase 6D
   PS-side LSM pipeline (which exists only because the HDL LSM chain
   wasn't wired up yet) and let the dashboard read NIDs directly from
   `lsm_status` / `lsm_nid` instead.

There is no rush on retiring the 6D PS-side path -- it doubles as a
useful sanity check during 6E.10 bring-up because both pipelines should
emit identical NID streams from the same `iq_dma` capture. The retirement
window opens once both decoders agree on a few hours of live capture.
